# SMS-to-Telegram Relay — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Minimal reliable backend (FastAPI + SQLite + one worker) on a RAM-starved VPS forwarding SMS to a private Telegram chat, plus an Android (Kotlin) transmitter app with direct-SIM fallback to an iPhone.

**Architecture:** One Uvicorn process on `127.0.0.1:8090` behind Caddy at `https://ai-barrow.ir/relay/*`; inside the process: API + a `getUpdates` long-poll task + a delivery-worker task. SQLite (`/var/lib/sms-relay/sms.db`) is the queue and audit log. Android persists first (Room), uploads via WorkManager with backoff, falls back to direct SMS via `SmsManager` in defined conditions only.

**Tech Stack:** Python 3.12, FastAPI, Uvicorn (1 worker), HTTPX, stdlib `sqlite3`; Kotlin (minSdk 26, compileSdk 35), Room, WorkManager, OkHttp; Caddy 2.8; systemd; pytest.

Spec: `docs/superpowers/specs/2026-10-21-sms-relay-design.md`. Working dir: `/root/sms-relay`.

## Global Constraints (verbatim-critical)

- VPS has ~2 GiB RAM, already ~75% used. NO Gradle/JDK/Android SDK/emulators/heavy test suites/Docker builds on this VPS. Backend unit tests (pytest, pure CPU) are allowed here only in `backend/.venv` (wheels only, no compilation: fastapi, uvicorn, httpx, pytest).
- Never kill/stop/reconfigure existing services (barrow-*, postgres, caddy, opencode-*, fail2ban, squid, microsocks, headroom). Caddy change = append `handle` block + `caddy validate` + graceful `caddy reload`, only at Phase 7 with explicit user confirmation.
- Never deploy local AI models. Never run more app workers/servers than specified.
- Secrets (`TELEGRAM_BOT_TOKEN`, `ADMIN_TELEGRAM_USER_ID`/chat id, tokens) never printed, never committed; copied from `/root/.config/opencode-telegram-bot/.env` into `/etc/sms-relay/env` (0640 root:smsrelay) at deploy.
- API base path `/relay` (Caddy strips prefix; backend mounts router at `/` inside app). Bind 127.0.0.1 only, port 8090.
- No SMS-content logging. Telegram sends never guaranteed exactly-once; use explicit `uncertain` state. No unbounded queues/loops; backoff cap 1 h, max 8 attempts.
- Repo commits: small, per task; never commit real creds, DBs, APKs (`.gitignore` covers).
- All new public exposure forbidden; only existing 80/443 via Caddy.

- `.github/workflows/android-build.yml`, `backend/requirements.txt`, `backend/requirements-dev.txt`

State machine: `received` (stored, not queued — pause/filter/hold) → `pending` (job enqueued) → `delivered` | `failed` (terminal) | `uncertain` (retries remain). Job rows removed on terminal states.

Filter behavior (`filters.py`): if `paused=1` → state `received`, no job. If sender in `block` → 200 `{accepted: false, reason: "blocked"}` and NOT stored. If `allow` non-empty and sender not in it → same. If body contains any `keyword` → same. Else store `pending` + enqueue.

Phone B fallback trigger contract (Android side): backend `/status` exposes per-message `state`; Android treats explicit state `failed` as confirmed failure (fallback allowed); `uncertain`/timeouts never trigger fallback.
